# 找人 (Find On-Call Person)

## 工作流程

### 步骤 1：查找值班人 (优先)

1. **获取模块列表**：静默执行 `/oncall --list` 获取所有可用的值班模块及其描述。
2. **匹配模块**：根据用户的具体问题描述，与获取到的列表进行语义匹配，找出最合适的 `<module>`。
   - *分支逻辑*：如果完全匹配不到合适的值班模块，请立即终止当前步骤，跳转至 **步骤 2**。
3. **获取值班人**：执行 `/duty <module>` 获取该模块的主备值班人。优先提取主值班人（列表的第一个人员）。
4. **工单创建判断**：
   - 仅当用户在上下文中**明确表达**了“拉群”、“建单”、“需要找他看问题”等意图时，直接提取问题描述作为 `<title>` (默认: "问题咨询")，执行 `/oncall <module> <title>`。
   - 若用户仅询问“谁负责”，则停止操作，直接汇报值班人结果。

### 步骤 2：基于组织架构查找负责人 (备选)

如果 **步骤 1** 无法匹配到对应的值班模块，则切换到组织架构检索路径，按以下流程精确定位负责人：

1. **加载部门索引**：阅读 `references/technology-center/README.md`，了解技术中心五大部门的划分。注意第 1 节"基础设施平台部门"已细分为 1.1 SRE Team / 1.2 区块链部门 / 1.3 Security Team 三个子小节，路由时需精确到子小节。

2. **匹配部门 / 子团队**：把用户关键词路由到 README.md 中**最具体的章节**（优先匹配第 1 节下的 1.1 / 1.2 / 1.3 三个子小节，再退回到第 2 / 3 / 4 / 5 节）。常见映射：
   - SRE / 监控告警 / EKS / EC2 / 发布 / 测试环境（部署） / 生产环境 / DBA / Redis / Kafka / 网关 / JumpServer / CI / 云权限 / 办公 IT → **第 1.1 节 SRE Team**
   - 区块链 / 公链 / 节点 / 钱包 / 签名机 / MPC / Pos / 资金托管 / 资金水位 / 链上对账 → **第 1.2 节 区块链部门**
   - Okta / Yubikey / WAF / HIDS / 邮件安全 / Apollo CR / JFrog / XSS / CSP / Akamai / 合约审计 / 上币审核 / DLP / 三方 SaaS 评估 → **第 1.3 节 Security Team**
   - 交易架构 / 基础架构 / 用户系统 / 撮合 / API / 行情指数 / 流数据 / 战略 / 工程效能 (Engineering Productivity) → **第 2 节 技术架构与战略部门**
   - 风控 / 大数据 / AI 中台 / 资金对账 → **第 3 节 数据 & 风控部门**
   - 测试（QA / 自动化测试 / 漏洞逃逸） / 移动应用 (Flutter) / Web 前端 / 组件库 → **第 4 节 前端、质量与效率部门**
   - 营销 / 现货 / 杠杆 / 充提币 / 划转 / 合约 / 借贷 / 理财 / 统一账户 / 法币 / 卡 / P2P → **第 5 节 资产、交易与市场部门**

   二义性提示：
   - "测试环境" 指部署/发布环境 → 第 1.1 节 SRE Team；"测试" 指 QA → 第 4 节 测试团队。
   - "工程效能 / Engineering Productivity" 仅归属 第 2 节，**不属于** 第 1.1 节。

3. **快速通道（仅当命中 第 1.1 节 SRE Team 时优先尝试）**：
   - 若问题涉及 **Gitlab 权限 / Code Review / GPG / 安全卡点 / Merge 报错 / 发布卡点 / 接口限制申请**，直接阅读 `references/technology-center/InfrastructurePlatformDepartment.md` 的 `### Gitlab 专项负责人地图` 小节定位负责人。
   - 若问题命中 22 类高频工单（发布 / EKS / EC2 / 网络 / DB / Redis / Kafka / 网关 / 告警 / 监控 / JumpServer / 大数据 / LiteLLM / CI / 云权限 / 办公 IT 等），先查 `InfrastructurePlatformDepartment.md` 的 `### 常见问题排查（速查表 + 历史工单 22 类高频问题）` 小节，命中即返回，无需通读全文。
   - 命中即结束 步骤 2；未命中则继续下一步。

4. **加载部门详情**：根据上一步匹配结果，仅阅读对应的**单个**部门详情文件：
   - 第 1.1 / 1.2 / 1.3 节 三个子小节均对应同一文件 → `references/technology-center/InfrastructurePlatformDepartment.md`
   - 第 2 节 技术架构与战略部门 → `references/technology-center/TechnicalArchitecture-StrategyDepartment.md`
   - 第 3 节 数据 & 风控部门 → `references/technology-center/Data-RiskControlDepartment.md`
   - 第 4 节 前端、质量与效率部门 → `references/technology-center/Frontend-Quality-EfficiencyDepartment.md`
   - 第 5 节 资产、交易与市场部门 → `references/technology-center/Asset-Trading-MarketingDepartment.md`

5. **定位负责人**：在部门详情文件中按"团队 → 模块 → 具体系统"的层级，匹配到最具体的负责人（`@姓名`）。若详情文件中存在更细粒度的"具体系统负责人"小节，优先采用最具体的人选；若仅给出团队负责人，则采用团队负责人。

6. **分支逻辑**：如果"快速通道"（第 3 子步骤）与"定位负责人"（第 5 子步骤）均无法匹配到合适负责人，立即终止当前步骤，跳转至 **步骤 3**。

### 步骤 3：查询知识库 (最终兜底)

如果 **步骤 1** 和 **步骤 2** 均无结果，调用search_knowledge_base工具，查询相关运维对接人信息。

## 输出格式

当你向用户回复最终结果时，**必须严格遵守**以下排版规范：
- **【严禁标题】**：绝对不允许使用 `#`、`##` 等任何级别的 Markdown 标题。
- **【极简汇报】**：仅输出客观结果，**绝对禁止**输出“下一步建议”、“可选操作”、“温馨提示”等附加段落。
- **【结构化引导】**：使用加粗文本引导结果区块。

**标准输出模板：**
**匹配结果：** [简明扼要地输出值班模块名称及对应的主值班人姓名/联系方式]

## 示例

**用户输入：** "数据库连不上了，帮我查下现在谁值班，拉个群看看。"
**内部执行：** 
1. 调用 `/oncall --list` 命令
2. 匹配到模块 `dba`
3. 调用 `/duty dba`，获取到值班人 **张三**
4. 用户明确要求拉群，调用 `/oncall dba 数据库连接异常排查`。

**最终回复：**
**匹配结果：** 已为您匹配到 `dba` 模块，当前主值班人为 **张三**。
**执行状态：** 已自动为您创建工单群并拉入值班人员，请在群内跟进处理。

## 注意事项

- **状态隔离**：每个步骤之间的工具调用结果仅作为你思考的上下文，不要将中间过程的大段 JSON 返回给用户。
- **失败兜底**：如果所有步骤均无法定位到负责人，请严格使用以下文案回复，不得随意发挥：“**查询结果：** 抱歉，暂时无法匹配到对应的负责人，请尝试提供更具体的业务线名称或使用其他途径查询。”
- **上下文复用**：在执行 `/oncall` 建单时，自动从用户的原始提问中提取 `<title>`，切勿反问用户“工单标题是什么”。
