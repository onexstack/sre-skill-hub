# 找人 (Find On-Call Person)

## 工作流程

> **路径优先级（重要）**：步骤 0 → 步骤 1 → 步骤 2 → 步骤 3 → 步骤 4。任一步骤成功命中即输出结果，不再执行后续步骤。步骤 0 用于精确实体（服务名 / IP）的直查，命中率高、噪音低，优先于值班模块匹配；步骤 4 是终极人工兜底（@Sunway Zhong），仅在前 4 步全部失败时进入。

### 步骤 0：精确实体直查 (服务名 / IP 优先)

当用户问题中**明确出现**服务名或 IP 实体时，先走精确直查路径。该路径直接命中具体实体的负责人，比基于值班模块的语义匹配更准确，因此置于最高优先级。

**触发条件（任一即可）**：

1. **服务名信号**：用户问题中出现形如 `<前缀>-<段>-<段>` 的小写带连字符标识符（如 `sre-os-apiserver`、`upex-gateway`、`market-data-service`），且上下文表达"谁负责 / 谁的 / 谁来看 / owner / 负责人"等找人意图。**仅有连字符标识符但无找人意图（例如纯粹报错日志粘贴）不触发**。
2. **IP 信号**：用户问题中出现合法 IPv4 地址（正则 `\b(?:\d{1,3}\.){3}\d{1,3}\b`，且每段 0–255），无论是否显式写"IP"二字，只要上下文是问"这台机器 / 这个节点 / 这个地址谁负责"即触发。

**执行规则**：

1. **服务名 → `/pod <服务名>`**：把识别到的服务名作为参数执行 `/pod <service-name>`，例如 `/pod sre-os-apiserver`。
2. **IP → `/ec2 <ip>`**：把识别到的 IPv4 作为参数执行 `/ec2 <ip>`，例如 `/ec2 10.247.10.175`。
3. **多实体处理**：若用户一次给出多个服务名或 IP，逐个执行命令并按"输出格式"场景 E 汇总返回；若混合服务名 + IP，分别走对应命令。
4. **结果判定**：
   - **命中**：命令返回了明确的负责人姓名 → 直接按"输出格式"场景 A（或 E，多实体）输出，**不再执行后续步骤**。
   - **未命中**：命令未返回结果、返回空、或返回提示该实体不存在 → 立即终止步骤 0，回退到 **步骤 1** 继续按值班模块 → 组织架构 → 知识库 → 人工兜底的完整链路处理。

**注意**：步骤 0 仅做"精确实体直查"，不替代步骤 2 的组织架构路由。例如用户问"Apollo 谁负责"虽然含有产品名，但 Apollo 不是 `<前缀>-<段>-<段>` 形式的服务名，不触发步骤 0；这类应继续走步骤 1 / 2。

### 步骤 1：查找值班人 (优先)

1. **获取模块列表**：静默执行 `/oncall --list` 获取所有可用的值班模块及其描述。
2. **匹配模块**：根据用户的具体问题描述，与获取到的列表进行语义匹配，找出最合适的 `<module>`。
   - **匹配判定**：仅当用户问题描述与某个模块的描述存在明确语义重合（关键词命中或同义词映射）时视为匹配成功。**模糊或低置信度的猜测不算命中**，应视为未匹配。
   - **未命中处理**：若模块列表中没有任何模块与用户问题对应，立即终止当前步骤，跳转至 **步骤 2**。
3. **获取值班人**：执行 `/duty <module>` 获取该模块的主备值班人。**主值班人 = 列表的第一个人员**。
4. **工单创建判断**：
   - 仅当用户在上下文中**明确表达**了"拉群"、"建单"、"需要找他看问题"等意图时，从用户原始提问中提取 `<title>` (默认: "问题咨询")，执行 `/oncall <module> <title>`。
   - 若用户仅询问"谁负责"，则停止操作，直接汇报值班人结果。

### 步骤 2：基于组织架构查找负责人 (备选)

如果 **步骤 1** 无法匹配到对应的值班模块，则切换到组织架构检索路径，按以下子步骤精确定位负责人：

1. **加载部门索引**：阅读 `references/technology-center/README.md`，使用其中的"路由关键词 → 详情文件锚点"表完成路由。**README.md 仅含索引，不含具体姓名**，所有姓名以详情文件为唯一事实源。

2. **匹配子团队**：把用户关键词路由到 README.md 中**最具体的子小节**（1.1 SRE Team / 1.2 区块链部门 / 1.3 Security Team）。具体路由规则与关键词列表已在 README.md 各子小节内维护，**本文件不再重复枚举**，避免双写漂移。

   - 1.1 SRE Team 下设 5 个子团队：自动化工具 & 平台基座建设、基础设施运维、稳定性和业务交付组、DBA、基础架构 (Performance Optimisation Team)。
   - 选定子团队后，再用 README.md 子团队表的"路由关键词"列做二次精匹配，落到具体小节。

3. **快速通道（命中即终止步骤 2）**：仅当路由到 **1.1 SRE Team** 时优先尝试，按以下顺序检查 `references/technology-center/InfrastructurePlatformDepartment.md` 的对应专项小节：
   1. **Gitlab 专项** (`### Gitlab 专项负责人地图`)：覆盖 Gitlab 权限 / SSH Key / Token / Runner 配置 / Code Review 配置 / 安全 Review / 后端 Review / GPG 签名 / GPG 加白 / Merge 报错 / 发布卡点 / 接口限制临时申请 / 代码发布检测项白名单。
   2. **Lark 审批指引** (`### Lark 审批指引地图`)：覆盖 N20 数据库申请 / N34 云平台账号 (AK/SK/Role/SSO) / N17 EAA 应用入口 / N30 测试环境访问 / N102 LiteLLM / M27 Jfrog / M29 运维门户 / M82 云枢网络白名单 / G09 OpenSearch / G23/G20/G33/G27 JumpServer 用户与资产 / G131 BKE 集群权限。命中后**仅输出对应审批编号与说明**，不输出"负责人"，因为这是审批流程指引而非找人。
   3. **基础架构 / 公共组件 SDK 专项** (`### 基础架构(Performance Optimisation Team)`)：覆盖中间件 SDK (Canal/Apollo/Eureka/xxljob) / 监控体系 (alter-hook/pside-car) / 全链路监控组件 (cat/skycat/rasp/skywalking) / 安全网关 (shenyu) / 业务网关 (upex-gateway) / Common包 / Redis SDK (Jedis/Lettuce) / upex-reactive-feign / RPC (Aeron/Netty) / Kafka & RocketMQ SDK / ETCD SDK / 多泳道 / 三方风控 (顶象/极验)。该团队默认负责人 @Petter Li，但行级条目通常已写明具体责任人，请优先取行级。
   - 命中即结束步骤 2；未命中则进入子步骤 4。

   > **中间件 SDK vs 实例分流**：当问题含 Kafka / RocketMQ / RabbitMQ / Pulsar 等关键词时，必须先按 InfrastructurePlatformDepartment.md「基础设施运维 → 中间件实例运维」内的"中间件 SDK/实例分流（强制规则）"判定路由。SDK 侧走基础架构小节，实例侧走基础设施运维组；两类限定词均未出现或同时模糊命中时，按"输出格式"场景 D 同时返回两侧主负责人。

4. **加载部门详情**：根据子步骤 2 的路由结果，阅读 `references/technology-center/InfrastructurePlatformDepartment.md` 中对应的 H2/H3 小节（1.1 SRE Team / 1.2 区块链部门 / 1.3 Security Team 三个方向均在同一文件）。

5. **定位负责人（粒度优先级）**：按以下顺序输出负责人，**只取一个粒度的结果，不混用**：
   1. 若详情文件中明确写出该子方向的**行级具体负责人**（小节列表项中以 `@姓名` 形式列出的人员），**优先返回该具体负责人**。
   2. 若仅有"团队负责人"（小节顶部的 `**团队负责人**: @姓名`），返回该团队负责人。
   3. 若行级条目给出多个 `@姓名` 列表：
      - **主负责人 = 列表的第一个**（与步骤 1 主值班人规则保持一致）。
      - 若用户明确要求"备份 / 二线 / 紧急联系人"，则返回列表的第二个。
   4. 若条目附注"最终请通过执行 `/duty` 找对应的 `<小组>` 小组值班人员"：在返回行级负责人的同时**附带提示用户执行 `/duty` 获取实时值班人**，因为该行人员可能为团队代表而非当下值班人。
   5. 若条目附注"紧急找 @X"或"紧急联系 @Y"：仅当用户问题中包含 **P1 / P0 / 紧急 / 故障 / 生产事故 / Down / 不可用** 等紧急关键词时附带返回紧急联系人，否则不返回。

6. **分支逻辑**：如果"快速通道"（子步骤 3）与"定位负责人"（子步骤 5）均无法匹配到合适负责人，立即终止当前步骤，跳转至 **步骤 3**。

### 步骤 3：查询知识库 (最终兜底)

如果 **步骤 1** 和 **步骤 2** 均无结果，调用 `search_knowledge_base` 工具兜底：

- **入参构造**：将用户原始问题中的核心名词（系统名 / 业务名 / 故障现象）拼成 query 字符串。
- **结果筛选**：取返回结果中**置信度最高且明确包含负责人姓名**的条目；若所有条目置信度均低或不含明确负责人，视为兜底失败，进入 **步骤 4**。

### 步骤 4：人工分配兜底（终极兜底）

当 **步骤 1 / 2 / 3 全部失败**时，把问题升级到人工分配：

- **兜底负责人**：**@Sunway Zhong**（负责接单后人工判断并分配到对应负责人）。
- 直接使用《注意事项》中的"失败兜底"文案回复，**必须在文案中明示已指派 @Sunway Zhong 进行人工分配**，避免用户卡在"找不到人"状态。

## 输出格式

当你向用户回复最终结果时，**必须严格遵守**以下排版规范：
- **【严禁标题】**：绝对不允许使用 `#`、`##` 等任何级别的 Markdown 标题。
- **【极简汇报】**：仅输出客观结果，**绝对禁止**输出"下一步建议"、"可选操作"、"温馨提示"等附加段落。
- **【结构化引导】**：使用加粗文本引导结果区块。
- **【数据真实性】**：仅输出数据源中**真实存在**的字段（姓名为 `@姓名`）。**当前数据源不含邮箱、电话、Slack 等联系方式，禁止编造**；如用户索取联系方式，回复"请通过 IM 搜索 @姓名 直接联系"。
- **【语种一致】**：默认中文回复。若用户提问全程使用英文，可切换为英文回复，但**姓名格式 `@Name` 保持原样不翻译**。

**标准输出模板（按场景选择其一）**：

**场景 A：仅询问"谁负责"**
```
**匹配结果：** 已为您匹配到 `<模块或方向>`，当前主负责人为 **@姓名**。
```

**场景 B：用户要求建单/拉群（步骤 1 路径）**
```
**匹配结果：** 已为您匹配到 `<模块>` 模块，当前主值班人为 **@姓名**。
**执行状态：** 已自动为您创建工单群并拉入值班人员，请在群内跟进处理。
```

**场景 C：返回主备或多人**
```
**匹配结果：** 已为您匹配到 `<方向>`，主负责人 **@姓名 A**；备份联系人 **@姓名 B**。
```

**场景 D：歧义无法消解，需用户二选一（如中间件实例 vs SDK）**
```
**匹配结果：** 您的问题涉及 `<中间件名>`，但未明确具体场景，请您确认后再继续：
- 若属于**实例运维**（broker 不可用 / 集群异常 / 网络不通 / Topic 管理），主负责人 **@姓名 A**。
- 若属于**SDK 使用**（客户端代码 / 消费积压 / 发送 timeout / 序列化），主负责人 **@姓名 B**。
**下一步：** 请补充具体描述，我将为您精确路由。
```

**场景 E：步骤 0 多实体（服务名 / IP）汇总**
```
**匹配结果：**
- 服务 `<service-name-1>` 的负责人为 **@姓名 A**。
- 服务 `<service-name-2>` 的负责人为 **@姓名 B**。
- IP `<ipv4>` 所属机器的负责人为 **@姓名 C**。
```

## 注意事项

- **状态隔离**：每个步骤之间的工具调用结果仅作为你思考的上下文，不要将中间过程的大段 JSON 返回给用户。
- **失败兜底**：如果步骤 1 / 2 / 3 均无法定位到负责人，请严格使用以下文案回复，不得随意发挥：

  > **查询结果：** 抱歉，暂时无法匹配到对应的负责人。已指派 **@Sunway Zhong** 进行人工分配，请同步将问题描述发给 @Sunway Zhong，或提供更具体的业务线名称以便重新匹配。
- **上下文复用**：在执行 `/oncall` 建单时，自动从用户的原始提问中提取 `<title>`，切勿反问用户"工单标题是什么"。
- **路径冲突时步骤 1 优先**：若用户问题既能命中 `/oncall --list` 中的模块，又对应步骤 2 的快速通道（如同时存在 `gitlab` 模块与"Gitlab 专项"），按工作流程开头的优先级，**先走步骤 1**。
- **步骤 0 优先于步骤 1**：若用户问题中同时出现服务名 / IP **和**值班模块关键词（例如"sre-os-apiserver 报错谁来看"），按工作流程优先级 **先走步骤 0**；步骤 0 命中即终止，未命中再回退到步骤 1。
- **步骤 0 不臆造服务名**：若用户问题中没有出现明确的小写连字符服务名 token（例如只是说"那个 API 服务"），不要凭猜测合成一个去调用 `/pod`，直接进入步骤 1。同理，IP 必须是合法 IPv4 才执行 `/ec2`。
